# Axiom — Final Technical Front-End Audit

**Original audit date:** 2026-09-02
**Current-state review:** 2026-09-04
**Archived:** 2026-09-04
**Project type:** Static multi-page marketing website (vanilla HTML/CSS/ES Modules, no runtime dependencies) with a custom Node release pipeline, a generated service worker, and Netlify-format static-hosting configuration
**Audit mode:** Repository-state review after the tracked P1, P2 and Extra work
**Current readiness:** Needs one minor release-integrity fix

## 1. Executive assessment

The implementation remains coherent, and the build/release layer is unusually disciplined for a static site. `tools/release/bundle-names.mjs` owns production bundle names, `dist/build-manifest.json` is the per-build source of truth consumed by the HTML rewrite, production Service Worker and generated cache-header rules, and `tools/qa/check-references.mjs` validates the source-side contract without a build. The current run passed over 1347 local references across 15 HTML pages, 20 CSS files, `manifest.webmanifest` and 11 statically checkable precache entries.

All four original P1 findings, all seven original P2 findings and all three Extra improvements were verified against their owning sources and remain correctly marked `RESOLVED` or `COMPLETED`. The focused Vitest/jsdom suite now covers the contact form, lightbox, mobile navigation and project-information/cookie modal; the current run passed 33 tests across four files. ESLint also passed. Static DOM inspection confirmed the document fundamentals across all 15 maintained pages, including unique IDs, resolvable ARIA references and 15 parseable JSON-LD blocks.

One minor release-integrity issue remains. Read-only re-derivation of the local Service Worker produced revision `5aeb3c3b22b4b154`, while tracked `sw.js` still contains `c7eff6c576b9f79e`; replacing that token makes the generated output byte-identical. The precache content itself is current, including `js/offline.js` and `js/theme-init.js`, so the resolved recovery and precache work has not regressed, but the stale revision can prevent a previously installed local worker from opening a new cache after canonical inputs change. This needs canonical regeneration and release validation before the repository is treated as a release candidate.

## 3. Verified strengths

- **Single-owner release contract.** `tools/release/bundle-names.mjs` owns every production filename decision, the hash algorithm, the manifest shape and its validation; `build:hash`, `build:sw` and `build:dist` all call into it rather than constructing names, and `readBundleManifest` rejects a stale, malformed or dangling manifest before any consumer acts on it.
- **Generated-file ownership is explicit.** `sw.template.js` is the only hand-edited Service Worker source and both profiles use the same renderer; the current drift at [P2-08] is detectable precisely because the canonical inputs and revision contract are deterministic.
- **Machine-checked reference integrity.** `tools/qa/check-references.mjs` resolves every local reference declared by HTML, CSS, the manifest and the statically available precache definition, and verifies the bundle contract without a server, browser or `dist/`. The current run passed.
- **Defensive initialization throughout.** Every module in `js/components/` returns early when its target element is absent (`js/components/navigation.js:7`, `js/components/lightbox.js:8`, `js/components/forms.js:7`, `js/components/cookies.js:7`), and all browser-storage access goes through `try/catch` wrappers (`js/utils/storage.js`).
- **Deliberate focus management with focused regression coverage.** The lightbox, project-information/cookie modal and mobile navigation implement focus movement/return and keyboard state management; the current jsdom run verifies those interactions together with the contact form in 33 tests.
- **Consistent document fundamentals across all 15 pages.** Static DOM inspection found one `<h1>`, `main#main`, a skip link, unique IDs, resolvable ARIA references and `alt` on every image in every maintained page.
- **Single canonical source for page metadata.** `tools/templates/pages.meta.json`, `head.partial.html` and the generator own every `<head>`; the current dry run produced no would-be page changes, and all 15 inline JSON-LD blocks parse.
- **Honest documentation.** `README.md` records the canonical origin without claiming that the current project is live there, declines unsupported WCAG/performance claims and links to the actual date-suffixed audit and plan archives.
- **Coherent, layered CSS with a small override surface.** One entry point aggregates tokens → base → layout → components → sections, with a `[data-theme="dark"]` override, a global `prefers-reduced-motion` block and 14 `!important` occurrences across 2867 lines.
- **No runtime npm dependencies.** `package.json` declares `devDependencies` only; fonts are self-hosted with their upstream OFL texts stored per family and indexed in `THIRD-PARTY-NOTICES.md`.
- **Security headers are comprehensive in source.** `_headers` declares CSP, HSTS, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Cross-Origin-Resource-Policy` and a restrictive `Permissions-Policy`; deployment delivery was not rechecked.
- **Public content declares its demonstrative character.** A project-information dialog appears on every page and the legal pages state that "Axiom Construction" is a fictional brand created for a demonstration project, so the marketing copy, testimonials and business details do not present themselves as a real trading company.

### [P1-01] Every canonical, social and sitemap URL names an origin that does not resolve

- **Status:** RESOLVED — implemented and recorded in CHANGELOG.md
- **Resolution:** The canonical public origin was corrected to `https://construction-pr02-axiom.netlify.app` and synchronized across generated metadata, JSON-LD, sitemap and robots configuration.
- **Current verification:** The obsolete origin has no occurrences in current tracked sources outside historical audit material. `tools/html/build-head.mjs` owns the public origin, its read-only dry run left all 15 heads unchanged, and current page metadata, JSON-LD, the 12 sitemap URLs and the `robots.txt` sitemap pointer use `https://construction-pr02-axiom.netlify.app` consistently.

- **Classification:** Contract mismatch
- **Affected area:** SEO metadata, social previews, structured data, deployment contract
- **Original evidence:** `tools/templates/pages.meta.json` — 30 `canonical` / `og_url` values; `tools/html/build-head.mjs:11`; `sitemap.xml:6` and the 11 further `<loc>` entries; `robots.txt:17`; the inline JSON-LD `@id` / `url` / `item` values in all 14 pages that carry a block. 254 occurrences of the origin across tracked sources.
- **Original behavior:** Every page declares `https://construction-project-02.netlify.app` as its canonical origin, its `og:url`, its `og:image` host and its structured-data identifier; `sitemap.xml` lists 12 URLs on that host and `robots.txt` points crawlers at its sitemap. That host was requested during the original audit and returned Netlify's "Site not found". The deployment supplied for the original audit answered on `https://construction-pr02-axiom.netlify.app`, served the same metadata verbatim, and declared `robots: index, follow` on its public pages.
- **Original impact:** On the live, indexable site every page told search engines that the authoritative copy lived on a host that did not exist, and the sitemap and `robots.txt` reinforced it with 12 more dead URLs. Because `og:image` and `og:url` resolved against the same dead host, link previews on social platforms and messaging apps failed to load an image or a destination — which for a portfolio-facing project defeated the main way the work gets shared. `README.md` already recorded that the repository did not confirm the project was live at that address, so the mismatch was unresolved rather than unknown.
- **Original recommended direction:** Establish one canonical origin that matches the deployment the project actually publishes, and set it in the places that own it: `pages.meta.json` (regenerating the heads), the hardcoded `defaultOgImage` in `tools/html/build-head.mjs`, `sitemap.xml`, `robots.txt`, and the inline JSON-LD identifiers. The origin currently lives in five independent places; consider making it a single declared value the generators read, so it cannot drift again.
- **Resolution verification criteria:** A request to the canonical origin declared by every page returns the deployed site; each page's `canonical` and `og:url` resolve to that page on that origin; `sitemap.xml` and `robots.txt` name the same origin; and the `og:image` URL returns an image. Repository consistency is verified; live URL and image availability were not rechecked in this review.

### [P1-02] The careers form collects personal data and a CV with no submission path

- **Status:** RESOLVED — implemented and recorded in CHANGELOG.md
- **Resolution:** The careers form is now an explicitly non-operational demonstration interface: all recruitment data and CV controls are disabled, the submission path was removed, and the page clearly states that real applications are not accepted or processed.
- **Current verification:** `legal/kariera.html` presents the demonstration notice in `#career-demo-notice`, associates it with `#career__form`, disables every data/CV/consent control, removes the form action and method, and uses a disabled `type="button"` labelled "Wysyłanie zgłoszeń niedostępne".

- **Classification:** Defect
- **Affected area:** Forms, public content integrity, `legal/kariera.html`
- **Original evidence:** `legal/kariera.html:156` (`<form id="career__form" action="#" method="post" novalidate>`), `:162-185` (fields, including the PDF upload at `:185`), `:188` (consent checkbox), `:195` (submit button)
- **Original behavior:** The page invited visitors to apply for a job ("Wypełnij formularz, aby zgłosić swoją kandydaturę") and collected name, e-mail, phone, position, a free-text experience description, a PDF CV upload and an explicit recruitment-consent checkbox. The form had `action="#"`, carried no `data-netlify` attribute, and no JavaScript module referenced `#career__form` or `.career__form` — `js/components/forms.js` bound only to `#contactForm`. Submitting therefore posted to the current document and nothing processed the data; no success state, error state or status message existed. `novalidate` additionally disabled the browser's own enforcement, so the `required` attributes on the name, e-mail and consent fields had no effect and the form could be submitted empty.
- **Original impact:** A visitor could upload a CV containing personal data, tick a data-processing consent, press send, and receive no indication that the submission went nowhere. The control was indistinguishable from a working application channel, which is the most consequential kind of misleading control on a public site — and the only page-level disclosure of the site's demonstrative character sat in the separate legal documents, not on this page.
- **Original recommended direction:** Either give the form a real destination on the same terms as the contact form (a named Netlify form with a confirmation route and the honeypot the contact form already uses) or replace it with an honest alternative — a mailto contact or a clearly disabled state that states no applications are accepted. Whichever is chosen, remove `novalidate` or supply the equivalent custom validation and error messaging, so required fields are actually enforced.
- **Resolution verification criteria:** Submitting the careers form either reaches a real destination and returns a visible confirmation, or the page no longer presents a submit control that implies processing; required fields block an empty submission with an announced error.

- **Current verification:** `offline.html` loads `js/offline.js`; that script wires retry, online-status announcement plus reload, and Escape reload. Both precache profiles and both revision-input lists include the script, and tracked `sw.js` contains it. The stale generated revision is separate and recorded at [P2-08].

### [P1-04] Most homepage content stays invisible when JavaScript does not run

- **Status:** RESOLVED — implemented and recorded in CHANGELOG.md
- **Resolution:** The reveal hidden state is now scoped to documents with the existing `html.js` enhancement marker, so reveal content remains visible without JavaScript while the existing scroll animation behavior is preserved when JavaScript is active.
- **Current verification:** `js/theme-init.js` adds the `js` marker before the application module loads, while the hidden reveal state is declared only by `:where(html.js) .u-hidden, :where(html.js) .hidden`; without that marker the content has no hidden start state. `js/sections/hero.js` continues to add `u-show` in the enhanced path.

- **Classification:** Defect
- **Affected area:** Progressive enhancement, CSS utilities, homepage and service pages
- **Original evidence:** `css/components/utilities.css:95-100` (`.u-hidden { opacity: 0 }`); `js/sections/hero.js:4-46` (the only code that adds `u-show`); `index.html` — 29 elements carry `u-hidden`; each of the six `services/*.html` pages — 13; `index.html:1211-1213` (`<noscript>`); `css/layout/layout.css:205-208` (the `html.js` guard used for the navigation)
- **Original behavior:** `.u-hidden` set `opacity: 0` unconditionally and was the start state of the scroll reveal. `u-show`, which restored opacity, was added exclusively by `js/sections/hero.js`. Measured in the browser against the original sources, all 29 `.u-hidden` elements computed to `opacity: 0` in the CSS-only state; with JavaScript running and the page visible, the reveal worked correctly on scroll. On the homepage those 29 elements were the About section text and feature list, all six service cards, all three testimonials and all twelve gallery items — everything between the hero and the FAQ. The rule carried no `noscript` fallback and no `html.js` guard, although `js/theme-init.js:3` set that very marker class and `css/layout/layout.css:205` already used it to guard the navigation drawer.
- **Original impact:** If the module bundle failed to load — through a cache miss against a hashed filename, a CSP change, a network error, or JavaScript being disabled — the homepage rendered its header, hero, FAQ, contact form and footer while the entire middle occupied layout space but displayed nothing. The failure was silent: no fallback, no error, no visual cue. The same applied to the feature, gallery and call-to-action blocks on all six service pages. The project otherwise treated a working non-JavaScript baseline as an intended property — the navigation was guarded by `html.js` and the contact form's own `<noscript>` stated that the form worked without JavaScript — so this was a gap in an established baseline rather than an unsupported expectation.
- **Original recommended direction:** Scope the hidden start state to the enhanced case, using the marker class `js/theme-init.js` already sets before first paint, so the reveal only ever hides content in a document where the script that reveals it has run.
- **Resolution verification criteria:** With JavaScript disabled, the About, Services, Testimonials and Gallery sections of `index.html` and the feature, gallery and CTA blocks of a service page are fully visible; with JavaScript enabled the scroll reveal behaves as it does today. The source contract is verified; rendered browser behavior was not rerun.

### [P2-01] `npm run build:head` is not idempotent and reformats every page on each run

- **Status:** RESOLVED — implemented and recorded in CHANGELOG.md
- **Resolution:** The head generator now normalizes retained script indentation and preserves each page's line-ending convention, making repeated `npm run build:head` executions byte-stable after the initial normalization.
- **Current verification:** A read-only execution of the real generator intercepted all 15 writes and compared each would-be result with the current page; all 15 were byte-identical and no repository file was written.

- **Classification:** Maintenance risk
- **Affected area:** Metadata generation tooling
- **Original evidence:** `tools/html/build-head.mjs:56-65` (`indentBlock`), `:67-79` (`extractHeadExtras`), `:98-103`
- **Original behavior:** `indentBlock` computed the minimum indentation across the retained block's lines, but the block's first line (`<script type="application/ld+json">`) was trimmed to zero indentation, so the minimum was always 0 and the fixed 4-space prefix was added on top of each line's existing indentation. Simulating the script read-only against `404.html`: the first run dropped the `<!-- JSON-LD -->` comment and grew the file by 74 bytes, and every subsequent run added a further 92 bytes as the JSON-LD block was indented four more spaces. All 15 pages changed on the first run.
- **Original impact:** The documented workflow for updating page metadata — "update `pages.meta.json` and regenerate through `npm run build:head`" — produced a 15-file diff dominated by whitespace regardless of what changed, and indentation grew without bound across runs. The metadata itself stayed correct, but the noise made real metadata changes hard to review and discouraged using the generator that owns the contract.
- **Original recommended direction:** Make the retained-block re-indentation idempotent — normalize the block's own indentation before applying the target prefix rather than adding to it — and preserve or deliberately drop the section comment, so a run with no metadata change produces no diff.
- **Resolution verification criteria:** Running `npm run build:head` twice in a row against unchanged `pages.meta.json` leaves all 15 pages byte-identical after the first run.

### [P2-02] `X-Robots-Tag: all` contradicts the `noindex` policy the utility pages declare

- **Status:** RESOLVED — implemented and recorded in CHANGELOG.md
- **Resolution:** The blanket `X-Robots-Tag: all` directive was removed from the global deployment headers, leaving the generated per-page robots metadata as the single indexing-policy source for HTML pages.
- **Current verification:** `_headers` contains no `X-Robots-Tag`; `404.html`, `offline.html` and `success.html` retain `noindex, follow`, and the same three policies are owned by `tools/templates/pages.meta.json`. Deployment headers were not inspected.

- **Classification:** Contract mismatch
- **Affected area:** Deployment headers, indexing policy
- **Original evidence:** `_headers:1-2` (`/*` → `X-Robots-Tag: all`); `404.html:11`, `offline.html:11`, `success.html:11` (`noindex, follow`); confirmed on the live deployment, where `/404.html` was served with `X-Robots-Tag: all`
- **Original behavior:** The `/*` rule applied `X-Robots-Tag: all` to every response, including the three utility pages that deliberately declared `noindex, follow` in their `<head>`. The repository set that page-level policy on purpose and recorded it in `docs/CHANGELOG.md`; the header had not been updated to match. Google resolves conflicting robots directives in favour of the more restrictive one, so `noindex` was expected to win there, but the site stated both policies for the same URLs and other crawlers were not guaranteed to resolve the conflict the same way.
- **Original impact:** The indexing policy for the utility pages depended on each crawler's conflict-resolution rule rather than on a single declared intent, and a reader of `_headers` was told the opposite of what `pages.meta.json` declared.
- **Original recommended direction:** Make the header layer agree with the page layer — either narrow `X-Robots-Tag` so it does not cover the utility routes, or drop the blanket header and let the per-page `<meta name="robots">` remain the single declaration of indexing policy.
- **Resolution verification criteria:** No response carries an `X-Robots-Tag` value that contradicts the `robots` meta of the page it serves. Source policy is verified; deployed responses were not rechecked.

### [P2-03] The dark-theme hover token uses `color-mix()` with a single colour

- **Status:** RESOLVED — implemented and recorded in CHANGELOG.md
- **Resolution:** The dark-theme hover token now uses a valid two-colour mix of `--surface-2` and `--feature-accent`, producing a distinct interactive background while preserving the existing light-theme and component behavior.
- **Current verification:** `css/tokens/tokens.css` now declares `color-mix(in srgb, var(--surface-2) 94%, var(--feature-accent) 6%)`; the same token remains consumed by feature/about/interactive cards and FAQ states, and `qa:references` passes.

- **Classification:** Source-visible risk
- **Affected area:** Design tokens, dark theme
- **Original evidence:** `css/tokens/tokens.css:123` (`--feature-hover-bg: color-mix(in srgb, var(--surface-2) 94%)`), against `:38` for the light-theme equivalent; consumed at `css/components/utilities.css:207`, `:218`, `:229` and `css/sections/faq.css:91`, `:112`
- **Original behavior:** The CSS Color grammar for `color-mix()` requires exactly two colour arguments; the dark-theme declaration supplied one. Measured in a Chromium-based browser, the value was accepted and resolved to a colour identical to `--surface-2`, so hovering a feature card, an about-list item or a FAQ entry in dark theme produced no background change at all — only the border and shadow responded. The light-theme token at line 38 was well formed and did shift the background.
- **Original impact:** The dark-theme hover state was incomplete where it was accepted, and in an engine treating the declaration as invalid the `background: var(--feature-hover-bg)` rule would fail at computed-value time and the hovered card would lose its background entirely rather than changing it. The behavior therefore depended on engine leniency for a construction the specification does not define.
- **Original recommended direction:** Give the dark-theme token a well-formed two-colour mix expressing the intended hover shift, matching the shape the light theme already uses.
- **Resolution verification criteria:** `--feature-hover-bg` resolves to a colour distinguishable from `--surface-2` under `[data-theme="dark"]`, and the hover background of a feature card, an about-list item and a FAQ entry visibly changes in both themes. The source correction is verified; rendered hover states were not rerun.
