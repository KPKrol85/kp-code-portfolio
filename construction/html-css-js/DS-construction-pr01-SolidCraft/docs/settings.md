# Pipeline & Tooling Settings

## Purpose

This file is the canonical source of truth for the Solidcraft build/development pipeline and tooling behavior.

## Tooling Overview

- Runtime baseline: Node.js `>=22.19.0`.
- Local dev server: dependency-free native Node.js server (`scripts/dev-server.mjs`).
- HTML composition: build-time partial renderer (`scripts/utils/partials.js`) expanding `partials/header.html` and `partials/footer.html` into every maintained page.
- CSS pipeline: PostCSS (`postcss-import`, `postcss-preset-env`, `autoprefixer`, `cssnano`) via `postcss-cli`.
- JS pipeline: `esbuild` (bundle + minify, target `es2018`, format `iife`).
- Image pipeline: `sharp` via `scripts/images.js`.
- Sitemap: `scripts/generate-sitemap.mjs`, invoked with `SITE_URL` supplied through `cross-env`.
- Service Worker: `scripts/generate-sw.js`, which derives the production precache list and cache version from the finished `dist/` tree.
- Formatting: `prettier`.
- Lighthouse: `lighthouse` + `chrome-launcher`, run by `scripts/qa-lighthouse.mjs` via `lighthouse.config.json`.
- Continuous integration: GitHub Actions, one workflow (`.github/workflows/ci.yml`).

## Scripts

- `start`: alias for `dev`.
- `dev`: runs `scripts/dev-server.mjs`, which serves the project locally on `127.0.0.1:15500`, opens the server root in the browser, and answers every HTML request through the shared partial renderer so `partials/` edits are visible on refresh. Live reload is delivered over Server-Sent Events: a CSS change refreshes stylesheets in place, any other source change reloads the page.
- `build:css`: builds `dist/css/style.min.css` and verifies no `@import` remains.
- `build:js`: builds `dist/js/theme-init.min.js` and `dist/js/script.min.js` and verifies no `import`/`export` remains in either.
- `build`: runs `build:css` and `build:js`.
- `build:sitemap`: scans real HTML pages and generates `dist/sitemap.xml`.
- `build:sw`: rewrites the marked manifest block in `sw.js` from the finished `dist/` tree and writes `dist/sw.js`.
- `watch:css`: watches `css/style.css` and rebuilds `dist/css/style.min.css`.
- `watch:js`: watches `js/theme-init.js` and `js/script.js` and rebuilds `dist/js/theme-init.min.js` and `dist/js/script.min.js`.
- `build:dist`: recreates `dist/`, renders every maintained HTML page with its `partials/` header and footer expanded, copies the optional runtime files and `assets/` (excluding `assets/img-src/`), and rewrites the HTML copies' references to minified assets; then runs `build` to generate the minified CSS/JS into `dist/`, then `build:sitemap` to generate `dist/sitemap.xml`, and finally `build:sw` to generate `dist/sw.js`.
- `images:build`: generates production images from `assets/img-src` into `assets/img`.
- `images:clean`: removes generated image outputs.
- `check:links`: validates broken internal/external links and missing anchors across all HTML files.
- `check:assets`: validates local asset references in HTML (`img/src`, `script/src`, `link[href]`, `source/srcset`, `img/srcset`).
- `check:html`: runs `check:links` and `check:assets`.
- `qa:a11y`: runs axe-based accessibility scans in a headless browser on key pages.
- `qa:functional`: runs `scripts/qa-functional.mjs`, a Playwright-driven functional regression pass over the navigation drawer, the offer submenu, the lightbox and the contact-form submission paths.
- `qa:lighthouse`: runs `build:dist` and then `scripts/qa-lighthouse.mjs` against `lighthouse.config.json`, serving `dist/` on an ephemeral loopback port and failing when a category falls below its threshold. `qa:lhci` is retained as an alias.
- `check:predeploy`: runs `check:html` and `qa:a11y` as the local pre-deploy gate.
- `format`: applies Prettier writes.
- `format:check`: validates formatting without writes.
- `check:links`, `check:assets` and `qa:a11y` each render pages through `scripts/utils/partials.js` before inspecting them, so they validate the same document `dist/` ships.

## Source vs Generated Assets

- Source assets (editable, canonical, used directly by local development):
  - `css/style.css` and `css/modules/**`
  - `js/script.js` and `js/modules/**`
  - `js/theme-init.js`
  - `js/sw-register.js`
  - `sw.js` (runtime logic only; the block between the `build:sw-manifest` markers is generated)
  - `partials/header.html` and `partials/footer.html`
  - `assets/img-src/**`
- Generated assets (pipeline outputs):
  - `dist/css/style.min.css`
  - `dist/js/script.min.js`
  - `dist/js/theme-init.min.js`
  - `dist/**/*.html` (maintained pages with their `partials/` header and footer already expanded)
  - `dist/sitemap.xml` (from `build:sitemap`)
  - `dist/sw.js` (from `build:sw`)
  - `assets/img/**` (from `images:build`)
- Rule: modify source files only; minified CSS/JS are production-only artifacts, exist solely under `dist/`, and are generated by the production build. The maintained source tree contains no `.min.css` or `.min.js` files, and `.gitignore` blocks `/css/*.min.css` and `/js/*.min.js` so they cannot reappear beside their sources.
- Shared layout markup has one source: `partials/header.html` and `partials/footer.html`. Maintained pages reference them with `<!-- @layout … -->` / `<!-- @include partials/… -->` directives; the expansion happens at build time, never in the browser. Edit the partial, not the rendered copy.
- `dist/` is generated output: it is recreated from source by `npm run build:dist`, is never maintained by hand, and is not tracked in Git. A clean checkout plus installed dependencies is enough to produce a complete `dist/`.

## QA / Validation

- CSS validation is embedded in `build:css` through `scripts/verify-css-build.js`.
- JS validation is embedded in `build:js` through `scripts/verify-js-build.js`.
- `build:dist` stages `dist/` first and then generates the minified assets into it through `build`; the verification scripts fail the build if a production asset is missing (`dist/css/style.min.css`, `dist/js/script.min.js`, `dist/js/theme-init.min.js`).
- Service Worker generation is self-verifying: `scripts/generate-sw.js` fails the build when a precache rule matches nothing (which is what running it before `build` looks like), when `sw.js` does not carry exactly one `build:sw-manifest:start` / `build:sw-manifest:end` pair, or when a derived entry is duplicated, out of sorted order, not a site-root web path, or does not resolve to a file in `dist/`.
- Partial rendering is itself a gate: `scripts/utils/partials.js` throws on a missing partial, an undeclared `{{variable}}`, a malformed or duplicated `@layout`, an `@include` escaping `partials/`, an include cycle, or any directive or `{{token}}` surviving rendering. Every caller — `build:dist`, `check:links`, `check:assets`, `qa:a11y`, `dev` — fails loudly instead of emitting an incomplete page.
- `format:check` is the formatting gate.
- A11y validation: `npm run qa:a11y` fails on `serious`/`critical` axe impacts, while `minor`/`moderate` are reported only.
- Run local pre-deploy regressions with `npm run check:predeploy`.
- `check:predeploy` and `qa:functional` also run automatically in CI; the contract is in "Continuous Integration" below.

## Continuous Integration

- One workflow: `.github/workflows/ci.yml`, workflow name `CI`, one job `quality-gate`. GitHub reports the status check as `CI / quality-gate`. Both names are part of the contract — branch protection selects a check by name, so renaming either silently detaches a required check.
- Triggers: `push` to `main`, `pull_request` targeting `main`, and `workflow_dispatch`. Development branches are not built on every push: a pull request validates a branch before merge, and `main` is validated independently of it.
- Runner: one `ubuntu-latest`. No OS matrix, no Node matrix, no browser matrix.
- Node: `24` LTS, pinned in the workflow only, tracking the current Active LTS line. `engines` is `">=22.19.0"`, the floor required by the Lighthouse QA tooling; the repository pins no version elsewhere (no `.nvmrc`, and `netlify.toml` sets no `NODE_VERSION`).
- Actions: `actions/checkout@v7` and `actions/setup-node@v7` only. `setup-node` supplies the npm cache, keyed on `package-lock.json`. No third-party action is used.
- Permissions: `contents: read`. No secret is read, nothing is written back to the repository, no release is created, and nothing is deployed — deployment stays with Netlify.
- Step order: `npm ci` → `npm run build:dist` → `npx playwright install --with-deps chromium` → `npm run check:predeploy` → `npm run qa:functional`. The build precedes the browser install because it needs no browser, so a broken build fails the job before the Chromium download is paid for.
- Dependencies are installed deterministically with `npm ci` from `package-lock.json`. `npm install`, `npm update` and any other dependency mutation are not used.
- Browsers: Chromium only, installed explicitly. The `playwright` package ships no install script, so `npm ci` downloads no browser on its own; Chromium is the only browser `qa:a11y` and `qa:functional` launch, so Firefox and WebKit are never installed.
- The workflow invokes existing npm scripts and never reproduces their internals in YAML. `check:predeploy` and `qa:functional` are separate steps so a failed run identifies which gate broke, and `check:predeploy` is not widened to absorb `qa:functional`.
- Concurrency: group `${{ github.workflow }}-${{ github.ref }}` with `cancel-in-progress: true`. Groups are already repository-scoped, and `refs/heads/main` and each `refs/pull/<n>/merge` are distinct, so a newer run cancels only the same ref's obsolete run and independent branches and pull requests never cancel each other.
- Timeout: `timeout-minutes: 15`. No step uses `continue-on-error`, so the first non-zero exit code fails the run.
- Deliberately absent from CI: `qa:lighthouse` and Lighthouse, `format:check`, Netlify deployment, artifact upload, coverage services, dependency-update automation, and any OS, Node or browser matrix.
- Making `CI / quality-gate` a required status check is a GitHub branch-protection setting rather than a repository file. It is performed by the maintainer and is not part of any npm script.

## Deployment Notes

- Deployment artifact is `dist/`, produced by `npm run build:dist`.
- The asset build is part of the deploy build: `build:dist` runs `npm run build` after staging `dist/`, so `dist/css/style.min.css`, `dist/js/script.min.js` and `dist/js/theme-init.min.js` are generated from the current sources on every deploy. No minified asset is ever committed.
- Sitemap generation is part of deploy build (`npm run build:dist`) via `npm run build:sitemap`.
- `scripts/generate-sitemap.mjs` requires `SITE_URL` and exits non-zero if it is missing. The `build:sitemap` script supplies it through `cross-env` (`SITE_URL=https://construction-pr01-solidcraft.netlify.app`), so no caller has to set it; overriding the variable is only needed for a different origin.
- `build:sitemap` includes real `.html` pages discovered from source and excludes non-indexable pages by default: `404.html`, `offline.html`, `thank-you.html`. Traversal skips `.git`, `.claude`, `.codex`, `node_modules`, `dist`, `build` and `partials`.
- `build:dist` renders all maintained HTML files through `scripts/utils/partials.js` and copies selected optional files when present (`_headers`, `_redirects`, `netlify.toml`, `robots.txt`, `manifest.webmanifest`, `js/sw-register.js`) plus `assets/` with `assets/img-src/` excluded. Traversal skips the same local directories as the sitemap scan (`.git`, `.claude`, `.codex`, `node_modules`, `dist`, `partials`).
- During `dist` build, HTML references are rewritten from source assets to minified assets. Public asset URLs are unchanged (`/css/style.min.css`, `/js/script.min.js`, `/js/theme-init.min.js`), so the precache contract, CSP and deployment model stay stable.
- Build order is deterministic and production-safe: clear `dist/` → render pages with their shared partials and copy static content → rewrite HTML references → generate production CSS/JS into `dist/` → generate `dist/sitemap.xml` → generate `dist/sw.js`. Nothing after the asset build touches `dist/` wholesale, so generated assets are never deleted by a later step. `build:sw` is last because it reads and fingerprints the files it precaches.
- The sitemap has exactly one producer: `scripts/generate-sitemap.mjs`, writing `dist/sitemap.xml` in the `build:sitemap` step. No `sitemap.xml` is tracked at the repository root and `build-dist.js` stages none, so no hand-maintained file can drift from or be silently overwritten by the published one. `robots.txt` keeps advertising the public `/sitemap.xml`, which the generated file serves.
- The production Service Worker has exactly one producer: `scripts/generate-sw.js`, writing `dist/sw.js` in the `build:sw` step. `build-dist.js` stages no `sw.js`, so nothing is copied for that step to overwrite. The root `sw.js` remains canonical for runtime logic; its `CACHE_VERSION` and `ASSETS` live between the `build:sw-manifest` markers and are owned by the build. In the source tree they are `"dev"` and `[]`, so the worker installs against the development server instead of requesting production-only minified assets that do not exist there; the deployed values are derived from `dist/`. The precache set is the app shell — every rendered page plus `/`, `manifest.webmanifest`, `dist/css/*.css`, `dist/js/*.js`, `dist/assets/fonts/*.woff2` and `dist/assets/img/favicon/*` — and everything else in `dist/` stays runtime-cached. `CACHE_VERSION` is a SHA-256 fingerprint over each precached URL paired with the SHA-256 of its bytes, truncated to 16 hex characters: no timestamp, random value or absolute path enters it, equal output yields an equal version, and any change to a precached file changes it. Cache ownership is unchanged: activation deletes only keys prefixed `solidcraft-v`.

## Repository Hygiene

- `.gitignore` keeps generated and local output out of Git: `node_modules/`, `/dist/`, the minified artifacts `/css/*.min.css` and `/js/*.min.js`, report output (`/test-results/`, `/playwright-report/`, `/.lighthouse-reports/`), the local agent worktree directories `.claude/` and `.codex/`, `.netlify/`, environment files, logs, editor directories and OS files. `assets/` and `package-lock.json` are intentionally tracked.
- `.gitattributes` declares one line-ending convention for tracked text files — `* text=auto eol=lf` — so line endings never appear as a diff. The binary extensions present in the project (`.avif`, `.ico`, `.jpg`, `.png`, `.webp`, `.woff2`) are marked `binary` so normalisation can never rewrite them; `.svg` stays under the text rule because it is XML.
- The tracked working tree is already normalised to that convention, so no renormalisation step is pending: `git ls-files --eol` reports `i/lf w/lf` for every tracked text file, no entry is `crlf` or `mixed`, and `git add --renormalize .` produces no change. Renormalisation would only become relevant again if `.gitattributes` itself changed; it is a Git operation performed by the maintainer and is not part of any npm script.
- `.prettierignore` excludes `partials/` (Prettier cannot parse the `{{token}}` / `{{#if}}` template syntax), `dist/`, and any `*.min.css` / `*.min.js`.

## Logging Hygiene (tooling scripts)

- Tooling scripts use `scripts/utils/logger.js`.
- Default output is concise (summary/errors).
- Verbose logs are opt-in via `--verbose` or `VERBOSE=1`.

Pipeline/tooling documentation lives only in `settings.md`. Keep pipeline notes out of separate docs to avoid drift.
