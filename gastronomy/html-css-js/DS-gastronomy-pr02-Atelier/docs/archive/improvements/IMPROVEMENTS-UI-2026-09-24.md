# Atelier No.02 — UI Improvements

**Analysis date:** 2026-09-24
**Project type:** Static multi-page website (frontend-only, vanilla HTML/CSS/JS; no backend service)
**Analysis mode:** Evidence-based UI improvement review
**Focus:** Project-wide UI

## Improvement overview

The project's interface is built on a deliberate design-token architecture — breakpoints, spacing, type scale, letter-spacing and shadow tokens are centralized in `css/base/tokens.css` and consumed through layered component and page stylesheets. The audit archived on 2026-09-23 (`docs/archive/audits/AUDIT-2026-09-23.md`) recorded no P0 findings, a passing full QA/accessibility pipeline, and subsequent P1/P2 resolutions or implementations subject to its stated verification limitations, including those retained for P2-01 and P2-06; this review does not repeat that ground.

The opportunities below sit inside that already-solid system: cases where an established pattern is not carried through to every instance that shares its role. The homepage hero heading falls back to the same type-scale step as its section headings, while the equivalent inner-page pattern already differentiates them. The lightbox's four controls ship below the 44px touch-target baseline the rest of the interactive surface already holds to. The About page's body copy is set in the widest letter-spacing step in the token scale — the step used elsewhere for short uppercase labels — while comparable body copy on the homepage uses a narrower one. The menu page presents its tag vocabulary through two visually unrelated chip styles depending on whether it is a filter control or a card badge. And three of the four vertical-rhythm tokens the project defines are never applied. None of these are rendering defects; each is a refinement available from tokens and patterns the codebase has already committed to.

## Proposed improvements

### IMP-UI-01 — Homepage hero heading shares its type-scale step with section headings

- **Affected area:** Homepage hero heading and section titles (`index.html`); global heading scale (`css/base/typography.css`).
- **Evidence:** `css/base/typography.css:398-406`; `css/pages/home.css:35-38`; `index.html:131`; `index.html:221,236,406,622,657`; contrast: `css/components/page-hero.css:31-39`; `about.html:178`.
- **Current state:** The base `h1` and `h2` rules in `css/base/typography.css:398-406` both set `font-size: var(--fs-2xl)` and `font-weight: 700`, with no other rule distinguishing them. On `index.html`, the page's single `<h1 class="hero__title">` (line 131, "Atelier No.02 — Fine Dining") is styled only by `.hero__title` in `css/pages/home.css:35-38`, which sets `margin-bottom` and nothing else, so it renders at the shared `--fs-2xl` size. Every section heading on the same page — `<h2 class="section__title">` at lines 221, 236, 406, 622 and 657 ("O Nas", "Sezonowe Menu", "Galeria", "Opinie Gości", "Kontakt") — renders at that identical size and weight. On the four inner pages that use the `.page-hero` component (e.g. `about.html:178`), the `<h1>` carries `.page-hero__title`, which overrides `font-size` to `var(--fs-3xl)` (`css/components/page-hero.css:33`), giving those pages' `h1` a size distinct from their `h2` section titles. The homepage hero does not use this component.
- **Proposed improvement:** Give the homepage's `<h1 class="hero__title">` its own font-size step above `--fs-2xl` (for example reusing `--fs-3xl`, the value `.page-hero__title` already uses on the other four pages), so the page's single top-level heading is visually distinguishable from its repeated `<h2>` section titles.
- **Expected value:** A visitor scanning the homepage gets a typographic cue for which heading is the page title and which are its subsections, consistent with the hierarchy the same token set already establishes on `about.html`, `menu.html`, `gallery.html` and `contact.html`.
- **Implementation scope:** `css/pages/home.css` (`.hero__title` rule only). No change to `.section__title`, to the `h1`/`h2` base rules consumed elsewhere, to markup, or to the hero's layout, color or spacing.
- **Acceptance criteria:** The computed font-size of `index.html`'s `<h1>` is larger than the computed font-size of its `<h2 class="section__title">` elements, and the homepage hero's layout, spacing and responsive behavior are otherwise unchanged.
- **Impact:** High
- **Effort:** Small
- **Status:** COMPLETED — Established a distinct homepage hero heading size using the existing `--fs-3xl` typography token.

### IMP-UI-02 — Menu tags render in two unrelated visual styles between the filter bar and the result cards

- **Affected area:** Menu page filter controls and menu card tag badges (`menu.html`); `css/components/cards.css`, `css/pages/menu.css`.
- **Evidence:** `css/components/cards.css:108-116`; `css/pages/menu.css:54-69`; `menu.html:657-663` (filters); `menu.html:724,774,824-825,887,937-938,988-989,1051,1101-1102,1152-1153` (matching card tags).
- **Current state:** `menu.html:657-663` renders seven filter buttons using the site's controlled tag vocabulary (`Wszystko`, `Wegetariańskie`, `Wegańskie`, `Bezglutenowe`, `Signature`, `Spicy`, `Bezalkoholowe`) as `.btn.btn--ghost.menu-filters__btn`, styled by `css/pages/menu.css:54-63`: a bordered, sentence-case chip at `--fs-xxxs` with `--ls-widest` tracking, with an active state (`:64-69`) that tints the border and background with `--burgundy`. The same vocabulary appears throughout the page as passive badges inside each menu card — e.g. `menu.html:724` (`Wegetariańskie`), `774` (`Bezglutenowe`), `887` (`Signature`), `1152-1153` (`Spicy`, `Wegańskie`) — styled by `.menu-card__tag` in `css/components/cards.css:108-116`: a borderless pill with a gold-tinted background, uppercase transform, and `--fs-xxs`/`--ls-wider`. The two components share no background, border, radius pairing, case treatment or size step, despite labelling the same categories.
- **Proposed improvement:** Bring the passive `.menu-card__tag` badge and the interactive `.menu-filters__btn` chip onto one shared visual language for the values they hold in common (a comparable padding/radius relationship, and a color or case treatment that visibly connects an applied filter to the badges it matches), while keeping the filter button's interactive affordance (border, active/pressed state) distinct from the card badge's passive presentation.
- **Expected value:** A visitor who filters by a tag can visually connect the chip they selected to the badges on the resulting cards, reinforcing that both represent the same underlying category rather than two unrelated pieces of UI.
- **Implementation scope:** `css/components/cards.css` (`.menu-card__tag` and its dark-theme variant) and `css/pages/menu.css` (`.menu-filters__btn` and `.is-active`). The button's `aria-pressed` wiring in `js/features/menu.js` and the filter/search behavior itself are out of scope and must keep working unchanged.
- **Acceptance criteria:** The tag badge and the filter chip for the same category share a consistent color, radius and case treatment, and the filter bar's active/hover/focus states remain visibly distinct from the passive card badges.
- **Impact:** Medium
- **Effort:** Medium
- **Status:** COMPLETED — Aligned menu filter chips and card tag badges with consistent typography and burgundy styling across light and dark themes while preserving their distinct roles.

### IMP-UI-03 — Lightbox controls fall below the site's established touch-target size on mobile

- **Affected area:** Gallery lightbox navigation and close controls (`gallery.html`, via `js/features/lightbox.js`); `css/components/lightbox.css`.
- **Evidence:** `css/components/lightbox.css:71-86` (`.lb-btn` at 34×34px); `css/components/lightbox.css:177-182` (44×44px only from `min-width: 760px`); `js/features/lightbox.js:35,44,50,56` (creates `.lb-prev`, `.lb-next`, `.lb-full`, `.lb-close` as `.lb-btn`); contrast: `css/components/nav.css:20-32` (`.nav-toggle`, 44×44px minimum), `css/layout/header.css:60-65` (`.theme-toggle`, 44×44px), `css/components/forms.css:78-82` (form fields, 44px minimum height), `css/components/nav.css:186-191` (`.nav__dropdown-toggle`, 44×44px on mobile).
- **Current state:** `js/features/lightbox.js` builds the lightbox's previous, next, fullscreen and close controls as `.lb-btn` elements. The base `.lb-btn` rule in `css/components/lightbox.css:79-80` sets `width: 34px; height: 34px`, and only the `min-width: 760px` media query at `:177-182` raises this to 44×44px. Below that breakpoint — phone-width viewports, where the gallery's touch and swipe handling is most directly relevant — the four controls render at 34px. Elsewhere in the same codebase, every other interactive control sized for touch is built to a 44px minimum: `.nav-toggle` (`css/components/nav.css:31-32`), `.theme-toggle` (`css/layout/header.css:64-65`), `.nav__dropdown-toggle` on mobile (`css/components/nav.css:190-191`), and form fields (`css/components/forms.css:78-82`).
- **Proposed improvement:** Raise the base (mobile-first) `.lb-btn` size in `css/components/lightbox.css:79-80` to the 44×44px minimum already used for every other touch control in the project, adjusting the `min-width: 760px` step at `:177-182` if a larger desktop-only size is still wanted.
- **Expected value:** The lightbox's four controls meet the same touch-target baseline the rest of the site already applies consistently, on the breakpoint range where touch interaction is most likely.
- **Implementation scope:** `css/components/lightbox.css` only (`.lb-btn` base rule and its `min-width: 760px` override). The `::before` icon mask size, control positioning (`.lb-prev`, `.lb-next`, `.lb-close`, `.lb-full`) and the lightbox's focus/keyboard handling in `js/features/lightbox.js` are unaffected.
- **Acceptance criteria:** `.lb-btn` computes to at least 44×44px at all viewport widths, and the lightbox's existing keyboard navigation, focus trapping and fullscreen behavior are unchanged.
- **Impact:** Medium
- **Effort:** Small
- **Status:** COMPLETED — Increased all lightbox controls to 44×44px across viewport sizes while preserving existing icons and interactions.

### IMP-UI-04 — About page body copy uses the system's widest letter-spacing step across seven text roles

- **Affected area:** `about.html` body copy (timeline, philosophy, suppliers, awards, location and FAQ sections); `css/pages/about.css`.
- **Evidence:** `css/pages/about.css:21` (`.timeline__text`), `:63` (`.philosophy-card__text`), `:131` (`.suppliers-card__text`), `:149` (`.awards-card__text`), `:177` (`.location-card__note`), `:183` (`.location-card__address`), `:213` (`.faq__answer`) — all `letter-spacing: var(--ls-widest)`; `about.html:806-807,822-823` (representative sentence-length heading/paragraph content); contrast: `css/pages/home.css:100-108` (`.about__text`, the homepage's own About-section paragraph, at `letter-spacing: var(--ls-wide)`); `css/base/tokens.css:70-74` (the tracking scale: `--ls-wider` 0.025em, `--ls-wide-plus` 0.035em, `--ls-widest` 0.05em, `--ls-eyebrow` 0.2em).
- **Current state:** `css/pages/about.css` applies `var(--ls-widest)` — at 0.05em, the widest step in the scale short of the dedicated `--ls-eyebrow` token — to seven different running-text roles: timeline descriptions, philosophy card text, supplier text, awards text, the location note and address, and every FAQ answer, several of which are full sentences (e.g. `about.html:807`, `822-823`). Elsewhere in the same token scale, `--ls-widest` is also used for short, uppercase, single-word or single-value labels (`.timeline__year`, `.suppliers-card__tag`), which is the conventional use for wide letter-spacing. The homepage's own About-section paragraph (`.about__text`, `css/pages/home.css:104`) — descriptive body copy comparable in role to the About page's own text — is instead set at `--ls-wide` (0.01em), five times narrower.
- **Proposed improvement:** Move the seven `about.css` body-copy roles listed above from `--ls-widest` to a narrower step already defined in the scale (for example `--ls-wide`, matching `.about__text`, or `--ls-wide-plus`), reserving `--ls-widest`/`--ls-eyebrow` for short uppercase labels as used elsewhere in the same stylesheet.
- **Expected value:** About page body copy gets a tracking value consistent with the same kind of content on the homepage and with how the rest of the token scale already distinguishes labels from running text, rather than the widest step in the system being the default for full-sentence content on one page.
- **Implementation scope:** The `letter-spacing` declaration in the seven `css/pages/about.css` rules listed above. Font-size, color, line-height, and the label rules that legitimately keep `--ls-widest` (`.timeline__year`, `.suppliers-card__tag`) are unaffected.
- **Acceptance criteria:** The seven listed body-copy rules in `css/pages/about.css` no longer reference `--ls-widest`, while the short uppercase label rules in the same file are unchanged.
- **Impact:** Medium
- **Effort:** Small
- **Status:** COMPLETED — Aligned letter spacing across seven About page body-copy roles with the existing --ls-wide typography token.

### IMP-UI-05 — Three of the four defined section-spacing steps are never applied

- **Affected area:** Site-wide vertical section rhythm (hero, standard sections, footer) across all 11 pages; `css/base/tokens.css`, `css/layout/layout.css`, `css/pages/home.css`, `css/layout/footer.css`.
- **Evidence:** `css/base/tokens.css:42-45` (`--section-y-sm`, `--section-y-md`, `--section-y-lg`, `--section-y-xl`); consuming rules: `css/layout/layout.css:24-26` (`.section`), `css/pages/home.css:2-5` (`.hero`), `css/layout/footer.css:1-2` (`.footer`) — all three read only `--section-y-md`; no rule elsewhere in `css/` references `--section-y-sm`, `--section-y-lg` or `--section-y-xl`.
- **Current state:** `css/base/tokens.css:42-45` defines a four-step vertical rhythm scale for section padding (`--space-8` through `--space-12`). Every section-level block that consumes one of these tokens — the generic `.section` wrapper used on every page, the homepage `.hero`, and the site `.footer` — reads `--section-y-md` specifically; the other three steps are not referenced anywhere in the stylesheets. In practice, every section on every page shares one vertical rhythm regardless of whether it is a page's opening hero, a standard content section, or a denser block.
- **Proposed improvement:** Apply the existing `--section-y-sm`/`--section-y-lg`/`--section-y-xl` steps deliberately — for example a taller step on hero/page-hero blocks and a tighter one on denser sections such as the menu filters bar or the footer's legal strip — using the scale the token system already defines, rather than leaving three of its four steps unused.
- **Expected value:** A graduated, intentional vertical rhythm that differentiates a page's opening section from its standard and denser sections, using tokens the project has already committed to in its design-token architecture.
- **Implementation scope:** The `padding` declaration on the handful of section-level selectors identified above (`.section`, `.hero`, `.page-hero`, `.footer`, and any other top-level section wrapper). No change to horizontal layout, `.container` widths, component internals, or the token values themselves.
- **Acceptance criteria:** At least one section type other than the current default consumes `--section-y-sm`, `-lg` or `-xl`; every section-level block still resolves to a defined token rather than a hard-coded padding value; page layouts otherwise reflow unchanged at all breakpoints.
- **Impact:** Medium
- **Effort:** Small
- **Status:** COMPLETED — Increased homepage and inner-page hero vertical spacing using the existing `--section-y-lg` token while preserving standard section and footer spacing.

## Selection summary

These five were selected for spanning distinct parts of the UI system — heading hierarchy, component-to-component visual consistency, touch-target sizing, body-copy typography, and layout rhythm — rather than five variations on one fix. Each is independent and can be implemented on its own without sequencing or shared dependencies. All five work entirely within tokens, components and patterns the project already defines (`--fs-3xl`, the 44px touch-target convention, the `--ls-*` scale, and the `--section-y-*` scale), so none introduces a new dependency, a new token, or a departure from the established visual identity. IMP-UI-01 and IMP-UI-04 are both typography-scoped but address unrelated mechanisms (heading size hierarchy on the homepage versus body-copy letter-spacing on the About page); IMP-UI-02 and IMP-UI-03 are both component-scoped but concern unrelated components (menu tags versus lightbox controls).

## Analysis limitations

This review is based on static inspection of canonical CSS, JavaScript and HTML source; no npm script was run, since every finding here is verifiable directly from source values (token definitions and their consuming rules) rather than from build or lint output. No rendered-browser verification was performed — computed sizes, spacing and touch-target geometry are as declared in the stylesheets, not measured on-screen or across browsers. No contrast, readability or usability metric was measured for IMP-UI-04; its rationale rests on the token scale's own internal convention (wide tracking used for short uppercase labels elsewhere in the same file) rather than a measured legibility claim. IMP-UI-05 assumes editorial intent behind the unused spacing steps; an equally valid response is to remove the unused tokens instead of applying them, which is a call for the project owner rather than something current evidence can settle.
