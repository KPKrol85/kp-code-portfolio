## 1. Original executive assessment (2026-09-19)

The engineering layer of this project is in good condition, and the full documented pipeline was executed successfully during this audit: lint, the source asset contract, HTML validation, the local link and fragment crawl, the pa11y-ci accessibility run, the production build, the production integrity check, production HTML validation and the production link and accessibility run all pass. Source and generated ownership is explicit and machine-enforced by `scripts/validate-dist.js`, which checks page inventory, transformed-HTML equality, service worker precache resolution, manifest assets and menu image variants, and rejects source files in the package. Every one of the seven P1 and nine P2 findings recorded in the archived 2026-09-17 audit was re-verified against the current code and is genuinely resolved; none are carried forward.

The remaining risk has moved out of interaction wiring into three other areas: public metadata and content that does not describe the page or the asset it points at, one maintenance command that is destructive in the current repository state, and two accessibility details that the configured automated checks structurally cannot see. `gallery.html` ships `about.html`'s social metadata and structured data, including an `FAQPage` whose questions appear nowhere on that page. `npm run images:build` would delete three tracked, referenced optimized images that it cannot regenerate, because one source filename is malformed. The menu page offers a PDF download that delivers a file whose own title is "Sample Menu Document". The contact form's focus indicator computes to roughly 1.8:1 in the default light theme, and the contact page is the one page whose demonstration dialog ships without `inert`.

None of these block the build, the production package or core navigation, and each has a small, local correction. The project is suitable for continued development now, and suitable for portfolio presentation or deployment once the five P1 items are closed.

- Failure isolation is consistent. Storage access is wrapped in `try/catch` in `js/features/theme.js`, `js/features/demo-modal.js` and the inline head script; `js/features/reveal.js` shows all content immediately when `IntersectionObserver` is missing; `js/core/scrollspy.js:87-137` keeps a scroll-offset fallback for the same case; `js/features/menu.js:38-40` degrades to the static cards when the fetch fails.
- Service worker runtime caching is scoped defensively. Non-GET requests and non-http(s) schemes are ignored, navigation is network-first with a cached-page then `offline.html` fallback, and `sw.js:72` stores a runtime response only when it is `status === 200` and `type === "basic"`, so opaque and failed responses are never cached.

The cookies policy enumerates the exact storage keys the code uses — `kp-theme`, `kp-demo-accepted`, the legacy `kp_demo_legal_ack` and the `atelierno02-v1.3` cache — states that no classic cookies are set, and explicitly states that the embedded map's loading is not gated on consent.

## 5. P1 — Important issues worth fixing next

### [P1-01] gallery.html publishes about.html's metadata and structured data

- **Classification:** Content integrity risk
- **Affected area:** SEO, social sharing, structured data
- **Evidence:** `gallery.html:8-10`, `gallery.html:29-30`, `gallery.html:39-40`, `gallery.html:76-150`
- **Current behavior:** The gallery page's `<title>`, `canonical` and `og:url` are correct, but the surrounding metadata block was copied from `about.html` and never re-targeted. `meta name="description"` is byte-identical to the About page's and ends with "zobacz zespół i filozofię"; `og:title` and `twitter:title` both read "O nas | Atelier No.02 – Fine dining, sezonowość i kuchnia autorska"; `og:description` and `twitter:description` describe the team and suppliers. The JSON-LD graph is the About page's: its `BreadcrumbList` second item is named "O nas" and points at `https://gastronomy-project-02.netlify.app/about.html`, and it declares an `FAQPage` with six questions whose visible counterparts exist only in `about.html:870` and below. `gallery.html` contains no FAQ content.
- **Impact:** Two of the eight indexed pages carry an identical meta description, every share of the gallery URL previews as the About page, the breadcrumb data contradicts the page's own canonical URL, and the page declares FAQ content that no visitor can find on it. How any particular search engine treats that last mismatch was not verified during this audit; what is verified is that the structured data served on `gallery.html` does not describe `gallery.html`.
- **Recommended direction:** Re-target the gallery page's description, `og:title`, `og:description`, Twitter equivalents and breadcrumb to the gallery, and remove the `FAQPage` node from a page that does not render those questions. The gallery page needs no FAQ node of its own; the FAQ and its structured data belong to `about.html`, where their content accuracy is addressed separately in [P2-02].
- **Verification criteria:** No two indexed pages share a meta description; `gallery.html`'s `og:title` and breadcrumb terminal item name the gallery and its own URL; no page declares structured data whose content is absent from that page.
- **Status:** RESOLVED — implemented and verified. Details are recorded in `docs/CHANGELOG.md`.

### [P1-02] npm run images:build would delete three referenced optimized images it cannot regenerate

- **Classification:** Defect
- **Affected area:** Image generation workflow, production assets
- **Evidence:** `assets/img-src/subpage-menu/desery/cytrusowe-ciasto-720x48-.jpg`, `scripts/images/build-images.js:101`, `scripts/images/build-images.js:54-58`, `menu.html:1406`
- **Current behavior:** `buildAll()` removes the whole `assets/img-optimized/` tree before regenerating it from `assets/img-src/`. Comparing the two trees, 503 of the 506 tracked outputs are reproducible; the three exceptions are `cytrusowe-ciasto-720x480.avif`, `.webp` and `.jpg`, because the source file is named `cytrusowe-ciasto-720x48-.jpg` instead of `cytrusowe-ciasto-720x480.jpg`. Running the documented command would delete those three tracked files and write `cytrusowe-ciasto-720x48-.{avif,webp,jpg}` in their place; `parseSizeFromName()` would also fail to match the malformed name, so the variant would not be resized. The same typo is why that item is the only one of 18 in `data/menu.json` without a 720 variant.
- **Impact:** A documented maintenance command is destructive in the current repository state. The three deleted files are referenced six times — by the static menu card at `menu.html:1406` and the featured dessert card on `index.html` — so `npm run qa:links`, `npm run qa:dist:integrity` and the 720w breakpoint would all break immediately after running it, and the originals are not recoverable from the source tree.
- **Recommended direction:** Correct the source filename so the generator reproduces the referenced 720x480 variants, and add the missing 720 variant entry for that item in `data/menu.json` so the rendered card offers the same candidates as the static fallback.
- **Verification criteria:** Every file under `assets/img-optimized/` is reproducible from a correspondingly named file under `assets/img-src/`, and `npm run qa` passes after `npm run images:build`.
- **Status:** RESOLVED — implemented and verified. Details are recorded in `docs/CHANGELOG.md`.

### [P1-04] Contact form focus indicator is effectively invisible in the light theme

- **Classification:** Defect
- **Affected area:** Contact form, keyboard accessibility
- **Evidence:** `css/components/forms.css:36-40`, `css/base/tokens.css:12`, `css/base/tokens.css:16`, `css/base/tokens.css:29`, `css/base/base.css:3-11`
- **Current behavior:** `.form input:focus-visible, .form textarea:focus-visible` sets `outline: 2px solid color-mix(in oklab, var(--burgundy) 30%, white)` with `outline-offset: 2px`. In the light theme `--burgundy` is `#6b1e2f`, so the outline resolves to `#d5b8bb`. It is drawn 2px outside the field, over the form panel's `--bone` (`#fffdf8`) and beside the field's `--input-bg` (`#ffffff`), giving 1.81:1 and 1.84:1 respectively — below the 3:1 ratio WCAG 2.2 SC 1.4.11 sets for non-text contrast. Because this rule outranks the `:where(...)` default in `css/base/base.css`, it is the only focus indicator these fields receive. The dark theme is unaffected: the same expression resolves to `#fce8ec` at 14.12:1 against `--input-bg` `#271c19`.
- **Impact:** On the site's only form, in the default theme, keyboard and switch users have no practical indication of which of the three fields holds focus. The configured pa11y-ci run cannot detect this, because it evaluates each page in its loaded state, so the gap is invisible to the existing pipeline.
- **Recommended direction:** Point the field focus rule at the existing `--focus-ring` token, or at another theme-aware value that clears 3:1 against both the field background and the surrounding panel in light and dark themes.
- **Verification criteria:** The computed focus outline on `#name`, `#email` and `#message` reaches at least 3:1 against both adjacent surfaces in each theme.
- **Contrast note:** These ratios were computed from the opaque hex tokens and the declared oklab `color-mix()`; they were not measured in a rendered browser.
- **Status:** RESOLVED — implemented and verified. Details are recorded in `docs/CHANGELOG.md`.

### [P1-05] contact.html ships the demonstration dialog without inert, leaving five hidden controls in the tab order

- **Classification:** Defect
- **Affected area:** Contact page, keyboard and assistive-technology behaviour
- **Evidence:** `contact.html:447`, `css/components/modal.css:1-11`, `js/features/demo-modal.js:86`, `js/features/demo-modal.js:102-118`
- **Current behavior:** Nine of the ten pages carrying `#demo-legal-modal` open the wrapper as `aria-hidden="true" hidden inert`; `contact.html:447` is the only one without `inert`. The `hidden` attribute is neutralised by `.demo-legal-modal { display: grid }` in the author stylesheet, so the dialog is kept out of sight by `opacity: 0; pointer-events: none` alone. `opacity: 0` does not remove focusability, so the panel's four links and its accept button stay tab-reachable. `openModal()` returns early when the acknowledgement is already stored, and the only call to `setModalInert(true)` is inside `closeModal()`, so for a returning visitor who has already accepted — and for any visitor without JavaScript — the attribute is never applied on this page.
- **Impact:** At the end of the contact page's tab order, keyboard users encounter five invisible controls with no visible focus indicator, inside a subtree marked `aria-hidden="true"` so screen readers announce nothing as focus moves through them. Activating the accept button in that state does nothing, because `closeModal()` exits immediately when the dialog is not open.
- **Recommended direction:** Ship the contact page's dialog wrapper in the same state as the other nine pages, and extend the existing source contract check so the initial dialog attributes are asserted rather than maintained by hand across ten copies.
- **Verification criteria:** All ten pages that carry `#demo-legal-modal` ship the wrapper with the same initial attributes, and no control inside the closed dialog is reachable by Tab on any page.
- **Status:** RESOLVED — implemented and verified. Details are recorded in `docs/CHANGELOG.md`.

## 6. P2 — Minor refinements

### [P2-01] Offline notices cannot appear on a page that is loaded while offline

- **Classification:** Defect
- **Affected area:** Connectivity feedback, offline experience
- **Evidence:** `js/features/network.js:44`, `js/features/network.js:47-48`, `js/features/network.js:9-28`
- **Current behavior:** `initNetworkStatusBanner()` seeds `lastState` from `navigator.onLine`, and `update()` returns immediately when the state is unchanged. Nothing calls `update()` at initialisation, and no other module renders these messages. A visitor whose page is served from the service worker cache while offline therefore starts with `lastState === false` and sees neither the status banner nor the two purpose-built hero notices in `setOfflineNotes()`, which explain that the menu is coming from cache and that gallery images may be missing. The messages can only appear if connectivity changes while the page is already open.
- **Impact:** The scenario the service worker exists to support is the one scenario in which the offline messaging never runs. On `menu.html` and `gallery.html` the visitor sees missing images with no explanation, on precisely the pages for which the code has a written explanation ready.
- **Recommended direction:** Render the offline state once at initialisation when the page starts offline, while keeping the restored-connection notice limited to genuine transitions.
- **Verification criteria:** Loading `menu.html` or `gallery.html` from cache with the network disabled shows the offline banner and the matching hero note, and a normal online load shows neither.
- **Status:** IMPLEMENTED — verification limited to the initialisation path. `initNetworkStatusBanner()` now renders the offline banner and the matching hero note once when a page starts with `navigator.onLine` false, and the restored-connection notice still requires a genuine transition; recorded in `docs/CHANGELOG.md`. The cache-served offline load named in the verification criteria has not been exercised, because `js/bootstrap.js` skips service worker registration on localhost and both QA servers bind to `127.0.0.1`.

### [P2-02] Public copy and the About FAQ describe services the project's own terms exclude

- **Classification:** Content integrity risk
- **Affected area:** Home, menu, about and contact pages, manifest, About page structured data
- **Evidence:** `contact.html:187`, `contact.html:199`, `index.html:199`, `menu.html:1741`, `manifest.webmanifest:88`, `about.html:870-911`, `about.html:96-147`, `regulamin.html:493-494`, `cookies.html:243`
- **Current behavior:** The contact page lead reads "Zarezerwuj stolik przez formularz", the section lead repeats "Zarezerwuj stolik lub wyślij nam wiadomość", the home hero and the menu call to action both present a "Rezerwacja" button, and the manifest shortcut is described as "Rezerwacje i kontakt z restauracją". The form those controls lead to contains only name, e-mail and message; it has no date, time or party-size input and no booking back end. The same pattern is present in the About page's FAQ, in both its visible markup at `about.html:870-911` and the `FAQPage` node at `about.html:96-147` that mirrors it: the six entries state reservation lead times ("Weekendy rezerwują się z dwutygodniowym wyprzedzeniem"), allergy handling requested "przy rezerwacji", group bookings for up to 20 guests with a private room, and gift vouchers that can be ordered "online — napisz do nas przez formularz kontaktowy". - **Impact:** The interface and the binding document on the same site describe different capabilities, and the terms specifically deny what the contact page lead and the About FAQ promise. A visitor following the copy expects the form to place a booking, and the FAQ additionally directs gift-voucher orders through the same form; only the legal pages state that neither is possible. Because the FAQ text is duplicated into structured data, the unavailable services are also published in a machine-readable form.
- **Recommended direction:** Align the reservation wording with the demonstrational character of the site and its contact form, without implying that any channel accepts binding reservations, so the interface and the terms agree. For the About page, the owner's decision is to replace the current restaurant-service FAQ with a project-focused FAQ describing the demonstration character of the site, the non-binding contact form, the demonstration menu, KP_Code Digital Studio's authorship and the front-end capabilities the project implements; the replacement is future implementation work, and its wording and structure belong in the development plan rather than in this audit. Whatever wording is adopted, the `FAQPage` node on `about.html` must be regenerated from it so the structured data and the visible FAQ continue to state the same thing. The page keeps its restaurant-portfolio presentation.
- **Verification criteria:** No public control, lead or FAQ entry promises a reservation, order or service the project does not provide; the wording no longer contradicts the terms; and every question and answer in the `FAQPage` node on `about.html` matches the FAQ text visible on that page.
- **Status:** RESOLVED — implemented and verified. Details are recorded in `docs/CHANGELOG.md`.

### [P2-04] Menu anchor links append a control label to 24 heading names

- **Classification:** Source-visible risk
- **Affected area:** Menu page, screen-reader heading navigation
- **Evidence:** `js/features/menu.js:406-441`, `js/features/menu.js:443-444`, `css/pages/menu.css:143-150`

### [P2-06] sitemap.xml lastmod values predate every current page revision

- **Relevant area:** `assets/fonts/`, `scripts/build-config.js` — `assetEntries`.
- **Current evidence:** `assetEntries` copies `assets/fonts` and `assets/icons` wholesale into `dist/`, so every tracked file in them ships regardless of whether the current release references it.
