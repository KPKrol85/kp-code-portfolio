- Derived the production service-worker cache name from the build instead of maintaining it by hand, closing the cache-versioning finding of the 2026-08-10 audit (`P2-02` in `AUDIT.md`). `RUNTIME_ASSET_URLS` already changed with every build that emitted new content hashes, but `CACHE_NAME` was a literal — `"fleetops-v1.12"` — that a maintainer had to remember to advance; when it was not advanced, a new build's `install` added its hashed assets to the cache the previous build was still using and the previous build's hashed entries stayed there permanently, because activation deletes only caches whose name differs from the current one and nothing else evicts them. That was storage growth across deployments rather than incorrect serving, since content-hashed URLs cannot collide, but it left the one half of the precache contract that no build-time check stood behind. `public/sw.js` no longer contains a version at all: it declares `CACHE_PREFIX = "fleetops-"` as the single definition of the namespace — used both to build the current cache name and to select the caches activation retires, where the prefix was previously repeated as a literal — and `CACHE_NAME = CACHE_PREFIX + (/* __FLEETOPS_CACHE_REVISION__ */ "dev")`, a second build placeholder alongside the existing `RUNTIME_ASSET_URLS` one. `fleetopsServiceWorkerPrecache()` in `vite.config.js` now replaces both when it emits `dist/sw.js`, and computes the revision from exactly the data it writes into the asset list: the first twelve hexadecimal characters of a SHA-256 digest over the newline-joined, deduplicated, sorted runtime asset URLs of the same bundle. Because Vite's content hashes are part of those URLs, the cache identity changes precisely when the precached asset set changes, and because the input is sorted and nothing reads the clock, a filesystem timestamp or a random source, two equivalent builds produce the same name and a byte-identical `dist/sw.js`; the current build emits `fleetops-e0407389859e`. The namespace stays owned by the maintained worker rather than split across two files, so the generated name cannot drift out of the range activation cleans up. The build fails loudly rather than silently degrading: a missing placeholder is reported by name and a revision that is not a well-formed digest is rejected, both through the plugin's existing `this.error` path, alongside the checks for a missing precached document or runtime asset. Every other service-worker contract is untouched — build-derived runtime asset precache, the `O-01` offline fallback and its self-sufficiency, `PH7-02` passthrough of a fulfilled navigation response of any status, offline recovery only after a genuinely rejected request, known-route navigation caching and cache-key normalization, stale-while-revalidate for static assets, and the install/activate lifecycle, which still retires every older `fleetops-` cache. No Workbox, `vite-plugin-pwa`, other dependency or separate build script was introduced, `dist/sw.js` remains a generated artifact that is never hand-edited or tracked, and development is unaffected: the plugin runs on build only, the maintained source keeps the `dev` revision, and the worker is still registered in production builds only. The identity deliberately tracks the runtime asset set rather than every precached byte — precached documents are stored under stable keys such as `/contact/` and are overwritten in place, so the hashed assets are the entries that would otherwise accumulate. One focused Playwright test joins the suite: it reads the emitted `dist/sw.js`, recomputes the revision from the runtime asset list in that same artifact independently of the plugin, and asserts the prefix, the sorted list, the derived name and that the maintained source still carries the placeholder and no `fleetops-v` literal, so neither half of the contract can change without the test failing. The README PWA sections (PL and EN) stop describing cache versioning as manual and record the derivation instead. Nothing was deployed and no Netlify configuration changed.
- Hardened the Content-Security-Policy in `public/_headers` with the three directives the self-only policy left implicit, closing `O-03`: `base-uri 'none'`, `form-action 'self'` and `object-src 'none'`. Document base URLs can no longer be redefined through an injected `<base>` element, HTML form submissions are restricted to the site's own origin, and plugin-style embedded content through `<object>` and `<embed>` is blocked. The six existing directives — `default-src 'self'`, `img-src 'self' data: blob:`, `style-src 'self' 'unsafe-inline'`, `script-src 'self'`, `font-src 'self'` and `connect-src 'self'` — keep their current values unchanged, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, `Strict-Transport-Security` and the cache rules were not touched, and no nonce, hash, Trusted Types, reporting endpoint or other directive was introduced. `base-uri` and `object-src` are `'none'` rather than `'self'` because the maintained source contains no `<base>`, `<object>` or `<embed>` element in any of the thirteen HTML entries and creates none at runtime. `form-action` is `'self'` rather than `'none'` because the contact form is a real submission path and it is same-origin: `#contactForm` declares `method="POST"` with no `action`, so the native no-JavaScript submission targets the document's own URL, and the enhanced path posts to the same-origin `/` through `fetch()`, which `connect-src 'self'` already governs. The other maintained form, the demo login, declares no `action` and prevents its own default, so it never navigates. Neither the Netlify Forms detection contract nor the form's JavaScript transport, honeypot or legal copy was modified to accommodate the policy. `public/_headers` remains the single maintained source and the emitted `dist/_headers` is a byte-identical `publicDir` copy, never a hand edit. Local verification covers the artifact only: `vite preview` serves `dist/` as plain static files and does not read `_headers`, so that the deployed site actually returns the extended policy — and that Netlify Forms continues to accept submissions under it — remains a post-deployment check. Nothing was deployed and no Netlify configuration changed.
